# Agent Note: GitHub 标签触发安装包发布

Status: implemented

## Problem

个人仓库只有带上游仓库限制的 Cask 更新流程，推送标签不会构建安装包。用户需要在自己的 GitHub 仓库通过标签自动生成 Release，而不是本地打包。

## Decision

`.github/workflows/release.yml` 监听版本标签推送，也接受手动指定已有标签。在 macOS runner 上调用现有构建脚本，构建 sing-box 双架构、校验 Mieru 官方下载文件，再生成三种架构的 ZIP 和 SHA-256 文件。构建脚本继续负责签名、架构及许可证检查，发布步骤仅在所有包构建并校验后执行。

版本从 vX.Y.Z 标签读取，checkout 固定到标签提交，使用当前仓库 GITHUB_TOKEN 发布到同名 Release。重复运行更新对应资产。工作流不依赖上游仓库身份，也不修改上游专用 Cask 发布流程。许可证全文下载增加有时限的重试，处理实际遇到的 TLS 下载失败。

## Alternatives considered

- 本地构建再手动上传：可以复用本机工具链，但不能满足用户要求的 GitHub 自动打包，因此采用标签触发的云端工作流。
- 为三种架构分别启动独立构建任务：可并行，但现有构建脚本始终先编译 Universal，重复任务会三次编译辅助程序。采用单任务复用缓存后分别打包。

## Consequences

推送新版本标签即可生成三个安装包和三个校验文件。每次首次构建需要下载 Go 依赖和辅助程序，受 GitHub macOS runner 及第三方下载服务可用性影响。仍为 ad-hoc 签名，不引入开发者证书或公证服务。

## Testing

工作流使用 actionlint 检查；构建脚本使用 bash -n 检查。最终发布状态以 GitHub Actions 的运行结果及 Release 六个资产为准。
